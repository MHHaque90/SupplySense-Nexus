# Data Strategy: SupplySense Nexus

## Overview

SupplySense Nexus operates on clearly labeled data sources. All data is categorized as public, synthetic, user-provided, derived, or simulated. This strategy ensures transparency, compliance, and trust in all analytical outputs.

## Data Source Categories

### Public Data
- **Definition**: Data available under open licenses with clear provenance.
- **Examples**: Government retail sales statistics, public holiday calendars, weather data.
- **Usage**: External factors for forecasting models.
- **Labeling**: `data_source_label = "public"`
- **Requirements**: License documentation must be maintained.

### Synthetic ERP Data
- **Definition**: Generated data that mimics real ERP patterns without corresponding to any actual company.
- **Generation Rules**: See "Synthetic Data Generation" section below.
- **Usage**: Product catalog, supplier network, inventory records, sales orders.
- **Labeling**: `data_source_label = "synthetic"`
- **Requirements**: No real company names, locations, or financial figures.

### User-Provided Data
- **Definition**: Data uploaded by platform users from their own systems.
- **Examples**: Company-specific inventory records, sales data, supplier information.
- **Labeling**: `data_source_label = "user-provided"`
- **Requirements**: User attests data accuracy and licensing.

### Derived Data
- **Definition**: Computed from other data fields.
- **Examples**: Days of supply, turnover ratios, forecast values, stockout probabilities.
- **Labeling**: `data_source_label = "derived"`
- **Requirements**: Derivation logic must be documented and reproducible.

### Simulated Data
- **Definition**: Generated by simulation models for scenario analysis.
- **Examples**: Disruption impacts, scenario outcomes, decision comparison results.
- **Labeling**: `data_source_label = "simulated"`
- **Requirements**: Always explicitly labeled in UI and API responses.

## Synthetic ERP Data Design

### Generation Rules

1. **Product Catalog**:
   - Generate 50-500 products across 5-15 categories.
   - Products have realistic names (e.g., "Widget A", "Component B-12").
   - No real brand names or trademarked terms.
   - Prices follow log-normal distribution centered around category averages.

2. **Supplier Network**:
   - Generate 10-50 suppliers across 5-15 countries.
   - Supplier names are generic (e.g., "Supplier North America", "Asia Pacific Components").
   - Lead times follow realistic distributions (7-90 days depending on category).
   - MOQs follow power-law distribution (some small, some large).

3. **Inventory Data**:
   - Inventory levels follow seasonal patterns with noise.
   - Safety stock calculated using standard formulas.
   - Transaction history spans 24 months.

4. **Demand Data**:
   - Base demand follows trend + seasonality + noise.
   - Seasonality: weekly, monthly, and yearly patterns.
   - Random events (promotions, holidays) create demand spikes.
   - All demand values are rounded to realistic quantities.

5. **Disruption Events**:
   - Generated with explicit probabilities and magnitudes.
   - Always labeled as "simulated" in all outputs.
   - Never presented as real events unless explicitly stated.

## Data-Quality Rules

### Completeness Checks
- Required fields must not be null (enforced by database constraints).
- Foreign key references must resolve to existing records.
- Date fields must be valid dates within acceptable ranges.

### Range Checks
- Quantities must be non-negative.
- Prices must be positive.
- Lead times must be within 0-365 days.
- Probabilities must be between 0 and 1.

### Uniqueness Checks
- Product SKUs must be unique.
- Purchase order numbers must be unique.
- Supplier names within an organization must be unique.

### Referential Integrity
- All foreign keys must reference existing primary keys.
- Deleting a supplier cascades to supplier_products and purchase_orders.
- Deleting a product cascades to demand_observations and inventory_snapshots.

### Temporal Consistency
- Order dates must precede shipment dates.
- Forecast dates must be after training window end.
- Inventory snapshots must be chronologically ordered.
- Audit events must have timestamps after creation dates.

## Missing-Data Handling

### Strategy
1. **Missing Demand**: Interpolate using seasonal patterns; flag as estimated.
2. **Missing Inventory**: Use most recent available snapshot; flag as stale.
3. **Missing Supplier Data**: Use category averages; flag as imputed.
4. **Missing Lead Times**: Use median lead time for supplier category; flag as estimated.

### Imputation Rules
- Never impute more than 20% of a dataset without flagging.
- All imputed values carry `data_source_label = "derived"` with imputation note.
- Missing data above 30% triggers data-quality alert.

## Outlier Handling

### Detection
- IQR method for numerical fields (values beyond 1.5 * IQR).
- Domain-specific rules (e.g., demand > 10x average for the same day of week).
- Statistical process control (values beyond 3 sigma from rolling mean).

### Treatment
- **Demand outliers**: Investigate for promotions or errors. If legitimate, keep with note. If error, cap at 99th percentile.
- **Price outliers**: Flag for manual review.
- **Lead-time outliers**: Flag supplier for scorecard review.
- All outlier handling is logged in data-quality checks.

## Referential Integrity

### Database Constraints
- All foreign keys have `ON DELETE CASCADE` or `ON DELETE RESTRICT` as appropriate.
- Unique constraints on natural keys (SKU, PO number).
- CHECK constraints on valid ranges (status values, probability ranges).
- NOT NULL constraints on required fields.

### Application-Level Validation
- Pydantic models validate all inputs before database writes.
- Integrity checks run as part of data-quality pipeline.
- Foreign key violations are caught and logged.

## Temporal Consistency

### Rules
1. **Ordering**: Events must be in chronological order within a product/warehouse.
2. **Overlapping**: Inventory transactions must not create negative stock unless explicitly allowed (backorder).
3. **Forecast Windows**: Training data must not overlap with test data.
4. **Audit Trail**: All temporal operations are logged with timestamps.

### Validation
- Run temporal consistency checks as part of data-quality pipeline.
- Alert on violations (e.g., forecast dates before training dates).
- Log all violations in `data_quality_checks` table.

## Data Lineage

### Tracking
- Every data record carries `data_source_label`.
- Derived records carry references to their source records.
- Simulation results carry the scenario ID, model version, and seed.
- All lineage information is stored in the `data_quality_checks` and `audit_events` tables.

### Lineage Example
```
demand_observations (synthetic)
  → features (derived)
    → forecast_model (simulated)
      → forecasts (simulated)
        → decision_comparison (simulated)
```

## Dataset Versioning

### Versioning Strategy
- Each dataset ingestion creates a new version.
- Version metadata stored in `data_quality_checks` and `forecast_runs`.
- Dataset versions include: row count, date range, checksum, data source label.
- Rolling window: Keep last 5 dataset versions for reproducibility.

### Reproducibility
- To reproduce any analysis, you need: dataset version + model version + seed.
- All three are stored with every analysis result.

## Privacy and Licensing

### Privacy
- No personal information is collected or stored.
- User data is isolated by organization.
- Audit logs do not contain sensitive business information.

### Licensing
- Public data must have documented open licenses.
- Synthetic data has no licensing restrictions (generated internally).
- User-provided data is governed by the user's license terms.
- All data usage is logged and auditable.

## Labeling Simulated and Synthetic Outputs

### Frontend Labeling
- All simulated results display a badge: "Simulated" or "Estimated"
- Chart data points distinguish actual vs. forecast vs. simulated
- Hover tooltips include data source label

### API Labeling
- Every API response includes `data_source_label` in the meta section.
- Forecast endpoints return interval estimates labeled as "simulated"
- Scenario results are always labeled "simulated"

### Documentation Labeling
- All documentation examples use clearly labeled simulated data.
- Example walkthroughs include explicit "Illustrative" labels.
- No simulated data is presented as real data anywhere.

### Audit Labeling
- Audit logs record when simulated data was used in decisions.
- Decision provenance includes data source labels.
- Governance reports aggregate data by source label.

## Phase 2 Implementation: Synthetic ERP Data Foundation

**This dataset is synthetic and is generated solely for demonstration, testing, analytics development, and portfolio purposes.**

### Generation Process
- Package: `backend/app/data/` with `config.py` (typed `GenerationConfig`), `generators/` (pure deterministic functions returning plain record dicts), `ingestion/` (batched async inserts in one transaction), `quality/` (structured checks plus reporting).
- Entry point: `python scripts/generate_synthetic_data.py generate --seed 42 [--reset] [--organization-count N --product-count N --supplier-count N --warehouse-count N --history-days N]`.
- Pipeline: generate → structural validation → batch insert → verify → quality checks → persist results → report. Any ingestion failure rolls back the whole dataset.

### Seed and Scale
- Default seed: 42; generator version 2.0.0. Same seed plus same configuration reproduces identical business fields (UUIDs and timestamps are assigned at ingestion and excluded from comparison).
- Default scale (laptop-friendly): 1 organization, 24 products, 8 suppliers, 3 warehouses, 365 days (2025-07-01 to 2026-06-30). Actual default counts: 26,280 demand observations, 22,022 sales lines, 21,095 inventory transactions, 689 purchase orders, 776 shipments, 5 disruptions.
- Scale-up is supported through the same CLI flags; batch size is configurable (`batch_size`, default 500).

### Data Provenance
- All operational records: `data_source_label = "synthetic"`. Disruptions: `"simulated"`.
- Schema truth: `disruption_impacts`, `bom_components`, `scenario_events`, `shipment_events`, `audit_events`, and `data_quality_checks` carry no `data_source_label` column in the Phase 1 schema; provenance for those rows is inherited from their parent records.
- Synthetic users use `@supplysense.local` addresses; `password_hash` holds a deterministic test-only marker, never a real credential.

### Key Generation Rules
- Demand: baseline + trend + yearly/weekly seasonality + noise + promo spikes, clamped non-negative; one row per product-warehouse-day; intermittent products include zero days.
- Sales: derived from demand (one order per warehouse-day), never independent.
- Procurement: baseline reorder-point policy (`reorder_point = avg_daily × lead_time × 1.2`); PO quantity ≥ MOQ and ≤ supplier capacity. This is a data-generation rule only, not an optimized policy.
- Inventory: chronological replay with receipts and capped fulfillment; stock never negative (shortfalls become lost sales and `partially_fulfilled` orders); opening balance booked as `OPENING_BALANCE` so `opening + receipts − sales + adjustments = closing`.
- BOM: finished goods consume lower-index components only (cycles impossible by construction) plus DFS validation; first component product is single-sourced, others multi-sourced; components are shared across products.
- Supplier reliability differs only via lead-time/delay parameters; no pre-assigned performance scores.

### Reset and Idempotency
- Without `--reset`, the pipeline refuses to duplicate an existing dataset (`DatasetExistsError`).
- With `--reset`, only the SupplySense synthetic tables are deleted in FK-safe order; unrelated databases, schemas, and `alembic_version` are untouched.

### Validation and Reporting
- 63 checks across completeness, validity, uniqueness, referential integrity, temporal consistency, range validity, business rules, and reconciliation; results persisted to `data_quality_checks` with PASS/WARN/FAIL status and severity.
- `report` prints real database counts; `sample` exports small CSVs to `data/sample/` plus the dictionary in `data/dictionaries/` (JSON and Markdown).

### Known Limitations
- Forecasts, scenarios, decision options, optimizations, model versions, and audit events are intentionally empty (later phases).
- Lost sales from stockouts are not backlogged; unfulfilled demand simply reduces sales.
- Each purchase order carries a single line item; split shipments share one schedule.
- Full-dataset validation takes several minutes on a developer laptop (measured honestly per run).
